# Задание 2. Целевая архитектура MVP с Privacy by Design

Файлы: `c4-mvp-privacy.drawio` (исходник для draw.io) и `c4-mvp-privacy.png` (картинка).

На диаграмме показано состояние MVP: пациент записывается к специалисту через портал, ресепшен видит записи, напоминает пациенту и врачу. Зелёным выделены новые блоки, которые добавлены ради Privacy by Design и аналитики. Пунктиром показано то, что появится после MVP (интеграция с лабораторией). 1С и ККМ в MVP не меняются.

## 1. Новые блоки Privacy by Design

| Блок | Что делает | Какой принцип обеспечивает | Закрывает проблемы (problems.md) |
|------|-----------|----------------------------|----------------------------------|
| IAM (Keycloak) | Единый вход, второй фактор, роли (RBAC) | Защита по умолчанию, наименьшие привилегии | P1, P2, P4 |
| API-шлюз (Kong, WAF) | Единая точка входа: проверка токенов, лимиты, проверка схем запросов, скрытие лишних полей | Защита по умолчанию, минимизация | P11, P15, P16 |
| Policy Engine (OPA) | Решение о доступе по атрибутам (врач ↔ пациент, филиал, цель обработки) | Наименьшие привилегии, ограничение цели | P2, P3, P16 |
| Сервис согласий и прав субъекта | Учёт согласий, отзыв согласия, удаление и сроки хранения, ответ на запрос пациента | Прозрачность, права субъекта | P20, P21, P22 |
| Каталог данных и теги (OpenMetadata) | Теги данных (PII/L3, PHI/L4, FIN/L2), lineage, политики на основе тегов | Data Lineage, управляемость | P6, P12 |
| Ключи и секреты (Vault, KMS) | Ключи шифрования по доменам, ротация | Шифрование данных | P5, P9 |
| Токенизация и псевдонимизация | UUID вместо ФИО, обезличивание | Минимизация, псевдонимизация | P7 |
| Аудит и мониторинг (Kafka, Elastic SIEM, VictoriaMetrics) | Неизменяемый журнал обращений, оповещения о нетипичном доступе | Подотчётность | P17, P18, P19 |

Дополнительно в самой архитектуре заложено:
- **Данные разнесены по доменам** (записи, ПДн, медданные), у каждого свой сервис, своё хранилище и свой ключ шифрования. Между сервисами ходит UUID пациента, а не ФИО.
- **Сервис уведомлений не получает ПДн**: пациенту уходит текст без персональных данных и ссылка на личный кабинет.
- **Каждый запрос идёт через шлюз**, поэтому новые интеграции (лаборатория, партнёры) не нужно проверять заново: они проходят те же проверки токена, роли и атрибутов.

## 2. Аналитический слой

Аналитика не читает рабочие базы напрямую. Путь данных такой:

1. Из доменных сервисов выгружаются только поля с тегом `analytics`; поля с тегом `no-export` (диагнозы и т. п.) наружу не выходят.
2. Обезличивание (Airflow, Spark) по тегам из каталога данных: удаление прямых идентификаторов, замена ФИО токеном, замена даты рождения возрастной группой, укрупнение адреса до города.
3. Озеро данных (S3, ClickHouse) хранит только обезличенные данные.
4. BI и ML-среда (Jupyter, BI) работает с озером через Apache Ranger: аналитик видит только разрешённые столбцы и строки.
5. Токен-сервис хранит связку «токен ↔ пациент» отдельно от озера, и аналитики к ней доступа не имеют.
6. Если пациент отзывает согласие, сервис согласий запускает удаление или повторное обезличивание данных в озере.

Так бизнес-аналитик получает данные для BI, ML и LLM без доступа к персональным данным, а компания не нарушает принцип ограничения цели обработки.
